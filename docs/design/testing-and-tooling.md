# Testing and Tooling

Design rationale for the repo's test infrastructure and mechanical tooling: the test-layer contract, the `packages/api` mock-db contract, web-side test gotchas, deterministic time, the `bun:sqlite` migration-test mechanics, the preview/dev seed-restore pipeline tests, mutation testing with Stryker, and `scripts/check-rules.ts`. The TDD workflow and quality bar live in [`AGENTS.md`](../../AGENTS.md); the layer table, reference patterns, mocking conventions, and detection-gate commands in [`.claude/rules/testing.md`](../../.claude/rules/testing.md); migration-authoring rules in [`.claude/rules/db-migrations.md`](../../.claude/rules/db-migrations.md). This doc records the *why* behind the shared infrastructure those documents point at.

## Test-layer contract

Why layers are pinned: the coverage sweep (PR #226) produced the same behavior fixed three times — the blind-level add / delete / game-set edit is asserted in `use-blind-level-editor.test.ts` (local hook), `blind-level-editor.test.tsx` (component, which mocks `@tanstack/react-query` wholesale and re-implements the patch derivation inside its `useMutation` stub) and `use-blind-levels.test.ts` (data hook) — and the same pending-flag pass-through in a page hook test and its page component test (`use-currencies-page` / `currencies-page`, `use-rooms-page` / `rooms-page`). Triplicated assertions triple the maintenance cost of every refactor without adding a single detectable fault. The first Stryker baseline (below) confirmed the inverse problem too: `packages/api/src/routers/session.ts` scored 55.8 % under near-total line coverage because its 2,585-line spec exercises Zod schemas and extracted helpers, not the procedures.

| Layer | Project | Fixes | Does not fix | Why the boundary sits here |
|---|---|---|---|---|
| Pure functions, Zod schemas, formatters | `web-node`, `api`, `db` | input → output, spec-named boundaries, error kinds | rendering, persistence | cheapest layer with the highest mutation kill rate; every boundary the spec names belongs here exactly once |
| API procedures via `createChainableMockDb` | `api` | ownership WHERE bindings, batch composition, `TRPCError` code, returned shape | SQL semantics, column lists, procedure existence | the mock records bound params but its `orderBy` / joins are no-ops (see the mock-db contract), so SQL behavior can only be proven by `bun:sqlite` specs — or, later, a real-SQLite integration layer |
| DB | `db` | FK `onDelete`, unique / partial indexes, CHECK constraints, migration behavior on `bun:sqlite` | column lists, `notNull` / `hasDefault`, Zod key sets | column shape is owned by `db:generate`; a test that restates it is a change detector, not a contract |
| Web hooks | `web-dom` | state transitions, handler outcomes, optimistic cache contents, contractual side effects | JSX binding | logic lives in `useXxx` by rule (`web-hooks-separation.md`), so the hook is the only place the logic can be asserted without the DOM in the way |
| Web components | `web-dom` | what the user sees per hook state, and that an interaction reaches the hook handler | hook logic through the DOM | a component test that mocks its own page hook can only prove the binding; anything else re-proves the hook test against a mock |

**The blind-level editor as the reference split.** `use-blind-levels.test.ts` (data hook, real QueryClient) proves optimistic cache contents and rollback; `use-blind-level-editor.test.ts` (local hook) proves add / delete / patch derivation; `blind-level-editor.test.tsx` proves only that each hook handler is reached from the UI and that each hook state renders its subtree. Before P2-web the component test re-implemented the patch derivation inside a wholesale `@tanstack/react-query` mock (1,419 lines, 41 `it()`), so its green depended on the mock agreeing with the hook — a change to the hook could not turn it red. The binding classes B1–B5 in [`testing.md`](../../.claude/rules/testing.md) generalize that split to every component that mocks its own page hook; nine test files still mock `@tanstack/react-query` wholesale after P2-web and are listed in that PR as follow-ups, which is why no mechanical check bans the pattern yet.

Zero-`expect` blocks are legitimate when a helper asserts (`expectRejects`, `findByText` throw on failure); the smoke-only check therefore flags blocks whose every `expect` ends in `toBeDefined` / `toBeTruthy`, never blocks without `expect`.

## The packages/api mock-db contract

[`packages/api/src/__tests__/test-utils.ts`](../../packages/api/src/__tests__/test-utils.ts) is the single home of the router-test infrastructure; extend it rather than hand-rolling a new pattern per test (AGENTS.md).

**`createChainableMockDb`** is a minimal chainable Drizzle-style mock `db` for exercising router procedures without a real database. Beyond resolving the rows configured per table, it records the bound params of every join and `where(...)` call on select/update/delete (`selectJoinParams`, `selectWhereParams` / `updateWhereParams` / `deleteWhereParams`) so **ownership scoping can be asserted** (SA2-176, SA2-183). Execution is **eager**, unlike a real DB: an insert is already recorded when `.values()` runs, and `db.batch([...])` just awaits already-resolved statements together (SA2-116).

**`evaluateWhere` is opt-in.** Enabling it makes `where(cond)` actually filter the configured rows through `cond` and `limit(n)` truncate them, so a procedure that pushes its whole predicate into SQL (rather than re-filtering rows in JS) can be exercised — the motivating consumer is `filter-preset.ts`'s `assertNameAvailable`, which does no JS re-filtering. Two deliberate constraints:

- **Only `and` / `or` / `eq` / `ne` are understood; any other operator throws** rather than silently matching, so an enabled mock can never quietly report a filter the query does not really apply.
- **Off by default** because fixtures written before this option assume `where(...)` is a no-op.

**The projection contract (c35).** A `select({ ... })` projection with a single-key aggregate (`{ maxSort: max(table.sortOrder) }`) collapses to one computed row like a real DB would. Every **other** select shape returns the configured rows unchanged — every existing fixture is written keyed by the query's **output** field names (including join projections that alias a joined table's column), so re-deriving keys from the Column reference would break that established convention.

**`expectProcedureSurface` is the only procedure-metadata assertion.** Router specs used to open with ten `expect(appRouter.x.y).toBeDefined()` probes plus one `expectType` / `expectProtected` pair per procedure — 120-odd `it()`s that could not fail unless a procedure was renamed, which the exact-key-set assertion already catches. `expectProcedureSurface(router, { name: type })` pins the key set, the protection, and the type in one place; the smoke-only check (below) rejects the probes.

**The mock-placeholder gotcha.** The mock's post-insert lookup does **not** filter by the freshly inserted id, so a create-path test whose procedure re-reads the row after inserting must seed a dummy pre-existing row for that table — otherwise the lookup resolves to nothing and the procedure's post-insert branch is silently never exercised.

**Callers and the three mock-db shapes.** `packages/api/src/__tests__/caller.ts` exports `createCaller({ userId, select, evaluateWhere })` — `createChainableMockDb` plus `appRouter.createCaller` with a fake session — and lives in its own module because `test-utils.ts` is imported by specs that `vi.mock` a constants module: pulling `appRouter` into `test-utils.ts` would load every router (and its schema imports) into those specs and break the module-wide mock. Two further mock shapes are deliberately separate exports rather than options on `createChainableMockDb`, because their lookup keys differ: `createReorderMockDb(rowsByTable: Map<table, rows>)` is keyed by the Drizzle table *object* and records `update().set().where()` params and `batch()` calls (the SA2-123 / SA2-176 reorder-scoping specs), and `createSequencedMockDb(selectSequence)` returns the next queued result per `select()` call regardless of table (the `live-session-pl` recalculation specs that walk several queries in a fixed order). A spec that needs a fourth shape extends this file; a single-use mock stays local to its spec.

## Seed tests: module replacement

A test that `vi.mock`s the seed-constants module gets its own file, because the mock is module-wide. The two dedicated specs exist precisely because the real `DEFAULT_GAME_*` data cannot express their scenarios: [`seed-game-data-chunking.test.ts`](../../packages/api/src/__tests__/seed-game-data-chunking.test.ts) needs a mix wide enough to overflow D1's 100-bind-param cap, and [`seed-game-data-unresolvable-variant.test.ts`](../../packages/api/src/__tests__/seed-game-data-unresolvable-variant.test.ts) needs a mix whose `variantKeys` do not all resolve to a seeded variant.

## Web test gotchas

### vi.mock factory hoisting (TDZ)

`vi.mock()` factories are hoisted **before** variable declarations, so a factory that closes over a module-scope `const` throws a baffling TDZ `ReferenceError` at runtime. Create every `vi.fn()` inline inside the factory, or via `vi.hoisted` (AGENTS.md's mocking conventions).

### The trpc/env stub pattern

Importing `@/utils/trpc` drags the env-validating import chain into module initialization, which crashes under jsdom where `import.meta.env` handling differs. So: modules whose unit tests exercise pure state lazy-load trpc, and jsdom tests of anything that transitively imports `@/utils/trpc` stub that module — providing a `queryFn` and rendering through `renderWithQueryClient` when the tree also contains real react-query hooks. The lazy `env` proxy that makes importing `packages/env`'s web schema safe in the first place is documented in [`web-platform.md`](web-platform.md).

### createTrpcMock and the queryKey shape

[`apps/web/src/__tests__/test-utils.tsx`](../../apps/web/src/__tests__/test-utils.tsx) exposes `createTrpcMock()`: an auto-materializing mock of the tRPC client/proxy shape — access any path (`mock.currency.list.query`) and receive a typed `vi.fn()`. Two contracts around it:

- A test that hand-mocks `queryOptions` must return a **stable queryKey of shape `[namespace, procedure, input]`** so key-derivation helpers (e.g. `getSessionQueryKeys`) resolve predictable keys, and must import the module under test **after** `vi.mock` so it picks up the mocked trpc.
- For hooks driven by a **real** QueryClient, the mocked `list.queryOptions(input)` must build an input-scoped queryKey plus a queryFn forwarding the input, so the real QueryClient can seed cache entries and refetch predictably per `screenKey`.

### The refetch-mirroring race (optimistic-rollback assertions)

In real-QueryClient tests of optimistic mutations (the `use-currencies` / `use-blind-levels` suites), the mutation's `onSettled` invalidation triggers a refetch, so a rollback assertion races the refetch: if the mocked queryFn serves its default (empty) payload, the refetch wipes the state `onError` just restored before the assertion runs — it passes or fails nondeterministically. The fix is structural, not a `waitFor`: **mirror the rollback state in the mocked queryFn** so the post-invalidate refetch reseeds the same data the `onError` handler restores. The per-test-overridable queryFn exists precisely for this.

## Deterministic time in tests

**`withTz`** ([`apps/web/src/__tests__/tz.ts`](../../apps/web/src/__tests__/tz.ts)) provides deterministic time-zone control for date-formatting tests (SA2-145 — CI/local divergence). Node/Bun re-reads `process.env.TZ` on every `Date` operation, so wrapping an assertion in `withTz` exercises a specific zone regardless of the host machine. Design points:

- The pristine host zone is captured once at module load and restored in a `finally`, so a test can never leak a zone into sibling files sharing the same worker.
- **When the host had no `TZ` set, the restore must actually delete the variable.** `process.env.TZ = undefined` coerces to the string `"undefined"`, which Node treats as an invalid zone and silently falls back to UTC (SA2-145) — leaking instead of restoring the pristine "no TZ" state. `Reflect.deleteProperty` is used because `lint/performance/noDelete` forbids the `delete` operator.
- Canonical zones: `TZ_WEST = "America/Los_Angeles"` (reproduces the original off-by-one bug), `TZ_EAST = "Asia/Tokyo"`, plus UTC itself.

The `mcp` Vitest project pins `env: { TZ: "Asia/Tokyo" }` for the same reason: date assertions must not depend on the host timezone, and a non-UTC zone makes any accidental local-getter usage fail loudly ([`.claude/rules/datetime-and-numbers.md`](../../.claude/rules/datetime-and-numbers.md)).

**Expiry fixtures are relative, never fixed dates.** `buildMcpSession` rejects expired tokens, so a hard-coded future timestamp turns the whole suite red once the clock passes it — fixtures compute expiry relative to `Date.now()`.

## bun:sqlite migration tests

Migration specs (`packages/db/src/__tests__/migration-*.test.ts`, `preview-seed-restore.test.ts`) run against `bun:sqlite` — a real SQLite engine, matching what D1 executes. `bun:sqlite` is only available in the Bun runtime, so CI runs these files in a dedicated **`bun test` step** ("Test migrations with Bun SQLite" in [`ci.yml`](../../.github/workflows/ci.yml)), while a `skipIfNotBun` guard makes Vitest's Node projects intentionally skip the bodies — the skip that creates the silent-green hole `scripts/check-rules.ts` closes (see below). Every such spec needs the fixed two-directive import waiver — TypeScript has no `bun:sqlite` types under the workspace's Node-flavored config, and the `Bun` global only exists at runtime in Bun:

```ts
// @ts-expect-error -- bun:sqlite only exists in the Bun runtime.
// biome-ignore lint/correctness/noUndeclaredVariables: Bun is a runtime global
```

`packages/db/src/__tests__/migration-test-utils.ts` carries `isBun` / `skipIfNotBun`, `splitStatements`, `applyStatements`, `applyThrough`, `applyAsD1Migration` (drops the `PRAGMA foreign_keys` line the way `wrangler` does) and `applyCompleteMigrationHistory`; it takes the `Database` instance as a parameter and never mentions `bun:sqlite`, because the listing check below scans the *spec files* for that string — moving the `require` into the helper would silently drop every migration spec out of the check. The shared `applyThrough(db, statements, marker)` helper applies only the statements up to and including the first one matching `marker`, **without** a transaction — exactly the state a production apply that dies mid-file leaves behind (`wrangler` streams statements and records the migration only after the last succeeds). The rules these specs pin — mid-file death, abort-proof backfills, self-healing retry — live in [`.claude/rules/db-migrations.md`](../../.claude/rules/db-migrations.md).

## The preview/dev seed-restore pipeline tests

[`preview-seed-restore.test.ts`](../../packages/db/src/__tests__/preview-seed-restore.test.ts) pins the semantics of a pipeline that lives in **two hand-copied workflow siblings**: `preview-deploy.yml` (new preview DB) and `dev-deploy.yml` (every deploy — the dev DB is dropped and recreated each time) both seed a brand-new D1 by applying every migration and then replaying a `--no-schema` dump of production. The trigger-collision story and the stash design are owned by [`.claude/rules/db-migrations.md`](../../.claude/rules/db-migrations.md); `bun run check:rules` separately asserts that every workflow performing the restore carries the stash. What the test file adds:

- **It pins both halves of the fix**: the collision is real (so nobody "simplifies" the trigger stash away), and stashing the triggers around the restore keeps the dump the single source of truth without leaving the DB permanently trigger-less. `readTriggers` in the test is **the exact query the seed steps run**; a post-seed write must still fire the compat trigger — the stash is scoped to the restore, not a permanent disarm.
- **The 0049-naming caveat.** Only the first test case names 0049's compat triggers; when the contract migration drops the legacy `games` mirror, that case stops throwing. The fix is to re-point it at whatever derived-table trigger remains (or delete the file once none do) — **not** to conclude the stash is unnecessary. Every other case reads live triggers out of `sqlite_master` and never names 0049.
- **Re-arm idempotency.** The workflows' re-arm file is `cat drop-triggers.sql restore-triggers.sql` — the drops are what make it idempotent. SQLite strips `IF NOT EXISTS` before storing DDL in `sqlite_master`, so the read-back CREATEs alone would abort on the first surviving trigger — and `wrangler d1 execute --file` stops there, skipping every CREATE behind it.

## Mutation testing (Stryker)

**Why and what the score means.** Coverage says a line ran; a mutation score says a test noticed when the line was wrong. Stryker rewrites one expression at a time (`<` → `<=`, `&&` → `||`, `return x` → `return null`, a string literal → `""`) and runs the tests that cover it; score = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage). `Ignored`, `CompileError`, and `RuntimeError` mutants are outside the denominator. The first pilot (pre-baseline, one file each): `packages/api/src/routers/session.ts` 55.8 % (1,660 mutants, 174 never reached by any test), `packages/db/src/constants/session-event-types.ts` 80.7 %, the four `apps/web/src/features/sessions/utils/*.ts` 83.4 % with `session-form-helpers.ts` at 56.5 %.

**Runner topology.** `@stryker-mutator/core` + `@stryker-mutator/vitest-runner` are root devDependencies pinned to an exact version (scores are only comparable across runs on the same mutator set; the runner also declares an exact peer on core). Stryker is hosted by Node 22+, not Bun: it forks worker processes over IPC, and the repo already runs Node-only tools as `node ./node_modules/<pkg>/bin/<x>.js`. [`scripts/mutate.ts`](../../scripts/mutate.ts) generates the per-project config into `reports/mutation/<project>/stryker.config.json` and spawns `node node_modules/@stryker-mutator/core/bin/stryker.js run <config>` (the positional config path; `--configFile` is not a Stryker CLI flag).

**Bun isolated-linker workaround.** Stryker's default `plugins: ["@stryker-mutator/*"]` is resolved by reading the `@stryker-mutator` directory next to core's *real* path, which under Bun's isolated install (`node_modules/.bun/...`) contains only `api`, `core`, `instrumenter`, `util` — the runner is a sibling symlink one level up and is never found. A directory path in `plugins` fails too ("Directory import not supported"). The script resolves the runner with `import.meta.resolve("@stryker-mutator/vitest-runner")` and passes the absolute path of its `dist/src/index.js`; the fallback is the root `node_modules` symlink. Never symlink into `node_modules/.bun` and never switch the linker to `hoisted` for this.

**Scope per project** (the `isSubject` predicates in [`scripts/mutate-projects.ts`](../../scripts/mutate-projects.ts) are the single source of truth):

- `api`: every non-test `.ts` under `packages/api/src` except the two wiring files in `API_EXCLUDED` — `context.ts` (Better Auth session lookup bundled with `db` and the API keys) and `routers/index.ts` (the `appRouter` composition plus `healthCheck` / `privateData`). The only tests that could reach their mutants are "the mock returns what the mock returns" and a namespace-existence probe, both of which the rules ban, so they were 0 % `NoCoverage` by construction and are left out of the denominator.
- `db`: `src/constants.ts`, `src/constants/*.ts`, `src/schemas/*.ts` — Zod and pure logic. `src/schema/**`, `schema.ts`, `index.ts` are declarative Drizzle tables whose only "detector" would be schema-shape tests, which the rules forbid; `migrations/**` is SQL. `constants/player-tag-colors.ts` is excluded as well (`DB_EXCLUDED`): it is a name list plus a Tailwind class map with no function or invariant, so its 25 mutants were permanently `NoCoverage` and could only be "killed" by a test that restates the class strings — the P2 sweep's reviewers refused that test, and the denominator was cleaned instead.
- `web-node`: the subjects of the `web-node` include globs (`src/utils`, `src/shared/lib`, `src/features/**/utils`) minus `utils/trpc.ts` (client wiring, mocked by every test) and the two files whose specs are pinned to `web-dom` (`login-continuation.ts`, `share-session.ts`) — in `web-node` they would be 100 % NoCoverage noise.
- `web-dom`, `server`, `mcp`, `env`, `auth` have no Stryker run (jsdom start-up cost and low mutation density); the detection review there is the manual three-flip in `/detection-review`.

**Modes.** `--changed` (default) maps `git diff --name-only <base>...HEAD` plus the working tree to projects: an implementation file mutates itself; a spec mutates its sibling implementation when one exists and is a subject, is ignored when the sibling is excluded, and widens to the whole project when no sibling can be derived (`src/__tests__/*.test.ts` in `api` / `db`, shared `test-utils`); `package.json`, `bun.lock`, the root `vitest.config.ts` widen every project. `--mutate <file>` targets explicit subjects; `--all --project <p>` re-measures a project. Incremental mode is on by default with `reports/mutation/<project>/stryker-incremental.json`; the differ carries forward results for files not mutated in the current run, so a changed-files run on top of a nightly file still yields a whole-project score, and `run.json` records which mode produced the number. `--force` ignores the previous results; `--no-incremental` runs without the file. `ignoreStatic: true` skips mutants in static (module-load-time) code — the pilot attributed 75 % of `session.ts`'s runtime to 56 such mutants. In-place mode is required because Stryker's sandbox copy links only the root `node_modules`, so workspace packages do not resolve inside it. The price is that **the mutated project's sources are rewritten on disk while a run is in progress** (`// @ts-nocheck` on every file under `<project>/src`, mutant-switching code in the mutated files): do not edit, lint, type-check, or commit until the run finishes, and end a run with Ctrl-C (SIGINT), which restores the originals. A SIGKILL leaves the rewritten sources behind with the originals under `.stryker-tmp/backup-*` — the script refuses to start while a backup directory exists, and recovery is `git checkout -- <files>` for tracked files plus copying untracked ones back from the backup. `disableTypeChecks` is scoped to the project's `src/**` for the same reason: with `true` Stryker stamps every TypeScript file in the repository.

**Time-zone tests and the worker-thread pool.** The runner hard-codes `pool: 'threads'` with one worker; a worker thread's `process.env.TZ` assignment does not reset V8's cached zone, so `withTz` (which the `web-node` suite relies on for the SA2-145 regression tests) silently keeps the host zone and the initial dry run fails on the first west-of-UTC assertion. Those tests live in `*-tz.test.ts` siblings that the Stryker-only config `apps/web/vitest.node.stryker.config.ts` excludes — the normal `web-node` project still runs them, and in the mutation report their subjects' zone-dependent branches show as `NoCoverage`, which is the honest signal. `check:rules` rejects `withTz` in any other `web-node` spec.

**Comparing scores.** Compare per file, never the project aggregate alone: `packages/db`'s aggregate is dominated by `constants/game-variants.ts` and `player-tag-colors.ts`, pure data tables whose 160+ literal mutants flip between `Survived` and `Ignored` (static) depending on how the surrounding tests touch the module at load time, and swing the project number by tens of points without any test changing its detection power. A P2 cleanup PR therefore reports the per-file rows of the files it touched plus the aggregate, and a file that is only data (no function, no invariant) is left at whatever the report says.

**Gate policy.** `thresholds.break` is 0: the score is reported on the PR (`Mutation Report` workflow, one sticky comment) and in the nightly summary, and never fails a build. Reasons: the baseline is low in places where the fix is a new test layer, not a rewritten test; equivalent mutants exist; static-mutant and jsdom cost make a per-PR full run impractical. A threshold is introduced only after the P2 cleanup PRs have moved the baseline. Coverage % is never collected.

**Ignore policy.** Decorative survivors (UI copy, toast / log / error `message` text when the `code` is asserted, icon and label maps, `className` strings) are silenced with `// Stryker disable next-line <Mutator>[,<Mutator>]: <why>` — a machine directive with a mandatory reason, the same class as `biome-ignore` under [`comments.md`](../../.claude/rules/comments.md). Ranged disables and `all` are rejected by `check:rules` because they hide domain mutants along with the decorative ones. Equivalent mutants use the same directive with a reason starting `equivalent:`.

**Reading survivors.** `Survived` / `NoCoverage` in `ConditionalExpression`, `EqualityOperator`, `LogicalOperator`, `ArithmeticOperator`, `BlockStatement`, `OptionalChaining`, `MethodExpression` inside validation, ownership WHEREs, arithmetic, state transitions, date handling, sorting, error-code selection, or batch composition mean a missing outcome assertion — not a missing spy. The pilot's concrete examples: `isHero: z.boolean().default(false)` → `true` survived 116 tests in the same file; `getSessionCurrentState`'s empty-events branch and its `sortOrder` tie-break were never reached; `formatDateForInput` (UTC getters) had no test at all; `validateSessionOwnership`'s "not found" and "other user" branches were unreachable through the router spec.

**CI.** [`mutation-report.yml`](../../.github/workflows/mutation-report.yml) runs on PRs to `dev`: a `plan` job asks the script which projects the diff affects, a matrix job runs `--changed` per project (restoring the newest nightly incremental file from the Actions cache so unchanged mutants are not re-run), and a `comment` job renders `bun scripts/mutate.ts summary` into one `## Mutation Report` comment (same find/update pattern as the preview-deploy comment). Every step that can fail is `continue-on-error`; fork PRs get artifacts but no comment. [`mutation-nightly.yml`](../../.github/workflows/mutation-nightly.yml) runs `--all --force` for the three projects at 18:00 UTC (03:00 JST) on `dev`, saves the incremental file to the cache and the reports as artifacts; a red nightly means the tooling broke, and blocks nothing. Both pin Node 22 via `actions/setup-node` because `engines.node` stays at `>=20.3.0` for wrangler. `web-node` runs with `isolate: false`; the runner forces a single-worker thread pool, so cross-file leakage shows up as `Timeout` / `RuntimeError` noise rather than wrong kills — re-run one file with `--no-incremental` before trusting an implausible survivor there.

## Test-reach metrics (why not line coverage)

`bun run test:metrics` ([`scripts/test-metrics.ts`](../../scripts/test-metrics.ts), pure parts in [`scripts/test-metrics-lib.ts`](../../scripts/test-metrics-lib.ts)) writes `reports/test-metrics.{json,md}`: `it()` count / `as never` count / wholesale `@tanstack/react-query` mocks per workspace, collected tests per Vitest project (`vitest list --json`), optional wall-clock suite durations (`--durations`), the Stryker metrics of whatever `reports/mutation/<project>/report.json` files exist with each project's lowest-scoring files, the list of source files no spec sits next to or imports, and the specs over 30 `it()` or 600 lines. `--compare <dir>` reads a saved snapshot (`<dir>/test-metrics.json` plus `<dir>/<project>/report.json`) and prints the before / after table; a file counts as regressed only when its score fell *and* its `Survived` or `NoCoverage` count rose — a `Killed` ↔ `Timeout` swap leaves the score unchanged by construction, and any other jitter is a re-run, not a revert.

**Why line coverage is deliberately absent.** Coverage measures that a line executed, not that a test would notice it being wrong; once suite size is held constant it correlates weakly with fault detection (Inozemtseva & Holmes, ICSE 2014), and Google's own use of it is as a locator of untested code rather than a quality score (Ivanković et al. 2019; SWE at Google ch. 12). This repo has the local evidence: the coverage sweep that grew the suite to ~6,900 `it()` left `routers/session.ts` at 55.8 % mutation score under near-total line coverage, and the cheapest way to move a coverage number is precisely the smoke and type-only test that P2 deleted. Adding `@vitest/coverage-v8` would also slow every project's run, `web-dom` most. The reach signals above keep the useful half of coverage — "nothing reaches this" — at the mutant and file granularity where it maps onto a concrete missing test.

**What a gap means.** A NoCoverage mutant or an untested file in domain logic (validation, ownership WHEREs, arithmetic, state transitions, date handling) is closed by a test that asserts the outcome. Pure wiring — `packages/api/src/context.ts`, `packages/api/src/routers/index.ts` — and data tables such as `packages/db/src/constants/player-tag-colors.ts` or `apps/web/src/features/statistics/utils/labels.ts` are either pinned by a single invariant test (unique keys, every key resolvable) when one exists or left out of the Stryker subjects / silenced with a `Stryker disable` directive, with the reason recorded here; the number is never the goal. The CI comment (`mutation-report.yml`) appends the same table from the `mutate` matrix job's artifact so the reach metrics ride along with the mutation score without a dependency install in the `comment` job.

**NoCoverage triage (the September sweep).** Every remaining NoCoverage mutant in `api`, `db`, and `web-node` was classified before any test was written, because "close every gap" would have recreated the smoke suite that P2 deleted. Three outcomes, applied in this order:

- *Test* — the mutant sits in validation, an ownership WHERE, arithmetic, a state transition, date handling, sorting, error-code selection, batch composition, or the content of a write (which row is inserted / updated), or the enclosing procedure's success path had never been invoked (`blindLevel.create` / `delete`, `tournament.archive` / `restore` / `delete` / `addTag` / `removeTag`, `liveCashGameSession.complete` / `reopen`, every `updateSnapshot`). Field pass-through in an `update` (`if (input.x !== undefined) data.x = input.x`) is pinned by one `it()` per procedure that passes every optional field and `toMatchObject`s the written row — one per field would be the padding the rules forbid.
- *Directive* — the branch is provably unreachable from its only call sites. The recurring shape is the **equivalent guard**: `noUncheckedIndexedAccess` forces `if (!events[i]) continue` on an element taken from a `findIndex(...) !== -1` result or from a dense `[...xs].sort()` array, or a private helper re-checks a condition its single caller already threw on, or a `default` arm sits under a TypeScript-exhaustive union. These get `// Stryker disable next-line <Mutator>: equivalent: <why>` on the source line so the report stops asking; a test would only prove the guard is dead.
- *Leave* — the only test that could reach the mutant would pin the mock rather than a behavior. Three families, listed here so the next sweep does not re-open them: (a) **vanished-row guards** after a write — `session.ts` `getById`'s `!enriched` and `update`'s `!updated`, `session-event.ts` `create` / `update` re-reads, `game-mix.ts` `update`'s re-select, `live-cash-game-session.ts` `resolveRingGameAssignment`'s second ownership check (the same `(id, userId)` `validateEntityOwnership` just passed) — reaching them means hand-counting the mock's `select()` order with `createSequencedMockDb`, which fixes the implementation's query sequence, not an outcome; (b) **pass-through wiring** — `stats.ts` `breakdown` returning `breakdownStats(rows)` as `{ groups }` when `breakdownStats` is pinned standalone; (c) **thin browser-API wrappers** — `seat-screenshot.ts` `fileToBase64` around `FileReader`, whose test would restate the stub. Their mutants stay `NoCoverage` in the report by design; `--compare` treats them as the baseline.


## scripts/check-rules.ts

[`scripts/check-rules.ts`](../../scripts/check-rules.ts) holds the deterministic conformance checks for the rules in AGENTS.md and `.claude/rules/*.md`. It runs in CI ([`ci.yml`](../../.github/workflows/ci.yml)), the Claude Code Stop hook, and manually via `bun run check:rules`.

**Standing invariant: only currently-green checks may live in the file.** A red check would block every turn (the Stop hook runs it after each Claude Code turn). Checks for known-but-unfixed issues wait here until their Linear issues are fixed — currently the ColorBadge / PlayerAvatar wrapper bans (SA2-112, SA2-119).

### Matching soundness (excludeLine × multiline)

Each pattern is tested against the whole file first — so multiline patterns can match — and then per line for reporting; `excludeLine` filters individual line hits. A file that matched as a whole while **no single line matched** is reported as a genuine multiline violation. The guard for that fallback is "no line matched at all", not "the check has no excludeLine": this stays sound when a check combines an `excludeLine` with a multiline pattern — a file whose every hit line is excluded is not reported, but a real cross-line hit still is.

### The bun:sqlite listing check

`bun:sqlite` spec bodies sit behind `skipIfNotBun`, so Vitest reports them as *skipped*, not failed — a spec also missing from ci.yml's dedicated `bun test` step **runs nowhere and reports green**. The check is a **cross-file existence assertion** (every `{apps,packages}/**/__tests__/*.test.ts` mentioning `bun:sqlite` must be named in the step), which is why it lives outside the file's generic `CHECKS` table. The glob spans **every workspace**, not just `packages/db`: tests are colocated next to code, so the next bun:sqlite spec plausibly lands in some other `__tests__/`, and `*` does not cross `/` — a narrower glob would let such a spec escape both this check and the `bun test` step, the exact hole the check exists to close.

### The D1 trigger-stash check (delta beyond db-migrations.md)

- **It matches on the restore itself** (`--file=dump.sql`), not on a workflow allowlist — the seed step is a hand-copied sibling across `preview-deploy.yml` / `dev-deploy.yml`, and a copy is precisely what prose cannot keep in sync, so matching the restore marker catches the *next* copy of the step too.
- **The three stash markers are asserted separately** because each is a distinct half of the fix; in particular a workflow that dropped without re-arming would leave the DB permanently trigger-less, so a missing re-arm must fail on its own.
- Implementation trap: `dot: true` on the Glob scan is load-bearing — Bun's `Glob` skips dot-directories by default, so without it the scan of `.github/` yields an empty set and the check reports green forever.

### Regex-design deltas

- **DB shape-assertion check** ([`testing.md`](../../.claude/rules/testing.md) owns the rule): it matches the Drizzle *metadata accessors* (`.notNull`, `.hasDefault`, `.dataType`, `.columnType`, `.primary`, `.onUpdateFn`, `getTableName(`, `.primaryKeys`) rather than `getTableColumns` or `.columns`, because constraint tests legitimately read `fk.reference().columns` / `index.config.columns` (through [`packages/db/src/__tests__/test-utils.ts`](../../packages/db/src/__tests__/test-utils.ts)) and the two incident pins (`variant defaults to DEFAULT_VARIANT_LABEL`, c12) read `.default`. Counting FKs or indexes ("has exactly N") is shape too — a count breaks on every legitimate addition and proves nothing about a policy — so those tests were removed with the column probes; the check cannot express that, so it stays a rule. The one deliberate exception is the column-*presence* test in `oauth-schema.test.ts` / `passkey-schema.test.ts`: better-auth's plugins, not this repo, read those columns, so their presence is an external contract rather than a restatement of `db:generate` output.
- **Focused / skipped-test check** ([`testing.md`](../../.claude/rules/testing.md) owns the rule): the paren is load-bearing — `describe.skip` as a *bare value* is the `skipIfNotBun` guard (`isBun ? describe : describe.skip`) that the bun:sqlite listing check depends on; requiring `\s*\(` keeps that legal while banning every call form (`it.skip(`, `describe.only(`, `test.todo(`). `xit` / `fit` need `\b` so `profit(` and `benefit(` are untouched. Biome's `noFocusedTests` exists but only warns and misses `skip` / `todo`, so it is not the enforcement.
- **Stryker directive check**: the negative lookahead encodes the only accepted shape (`next-line`, one or more mutator names, a colon, a reason); uppercase-initial mutator names exclude `all`. `DIRECTIVE_LINE` whitelists `// Stryker disable` / `// Stryker restore` for the comment policy for the same reason `biome-ignore` is whitelisted — a reasoned machine directive is not prose.
- **Stryker-instrumentation scanner**: `stryNS_*` / `__stryker__` / `__STRYKER_ACTIVE_MUTANT__` or a bare `// @ts-nocheck` line in `apps/**` or `packages/**` (the generated `routeTree.gen.ts` is the one legitimate `@ts-nocheck`). In-place runs rewrite the sources on disk and restore them only on a clean exit or SIGINT; a `git add -A` while a run is active — even one started by a different agent in the same checkout — commits the instrumented files, and nothing else fails on them (`@ts-nocheck` silences `tsc`, the instrumented code still runs, and the comment policy whitelists the directive). Added after P2-web committed 87 such files from a concurrent `--mutate session.ts` run.
- **Smoke-only scanner** ([`scripts/check-rules-tests.ts`](../../scripts/check-rules-tests.ts), wired over `packages/**` and `apps/**` by the P2 cleanup PRs; `apps/server` had zero hits when the glob widened): the line-oriented `CHECKS` driver cannot express "every matcher in a block", so the detector masks strings, template literals, comments and regex literals first (same length, newlines preserved), then walks each `it(` / `test(` / `it.each(...)(` body and follows every `expect(...)` chain to its terminal called matcher. A block is a hit only when it has at least one `expect` and all of them end in `toBeDefined` / `toBeTruthy`; blocks without `expect` are never hits (helper-asserted specs). `not.toThrow` is deliberately not in the set: the `bun:sqlite` migration specs prove constraint acceptance by not throwing. `toBeUndefined` is also excluded — it flags dozens of legitimate "leaves X undefined" outcome tests.
- **Inline model-id check** (the rule and its why are owned by [`.claude/rules/ai-models.md`](../../.claude/rules/ai-models.md)): it bans **quoted `claude-*` literals wholesale** rather than enumerating generation names — an enumeration would miss the old digit-first id format (`claude-3-5-sonnet-20241022`). Requiring the quotes keeps `.claude/rules/...` paths and prose out of scope; workflow YAML is excluded because `--model opus` is a movable alias, not a pinned ID.
- **MCP direct-DB-import check** ([`.claude/rules/mcp-tools.md`](../../.claude/rules/mcp-tools.md) rule 2 owns the rule): the pattern matches the `@sapphire2/db` **prefix**, so barrel imports (`createDb` / schema re-exports) are blocked as well as subpath imports — matching subpaths only would let the bare barrel import pass.
