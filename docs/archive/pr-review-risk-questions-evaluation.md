## 方法

- 対象は #723・#728・#730・#740。各 PR の head だけを含む clone を作り（後のコミットは含まない）、`origin/dev` を merge-base に置いた。依存は head の lockfile でインストールした。
- 各 PR を旧プロンプト（当時の `lean.md` と `SKILL.md`）と新プロンプトで 1 回ずつ、Fable 5.2 / high で再生した。計 8 回。投稿なし、子エージェントなし、CI と同じコマンドに制限。Linear issue と PR 本文は当時の内容を渡した（#740 は当時と同じく issue なし）。
- 新プロンプトのリスク質問は、ルールファイルと、対象 4 PR 以外で見つかった指摘から作った。対象 4 PR だけで見つかった種類（移行後の行と API の不整合、画面が示す事実、セッションの鮮度）はこの測定では質問に入れていない。
- 採点は全体レビューの指摘と照合し、新しい主張はコードで確かめた。

## 読み取れること

- 改善の大半はモデルと effort の切り替えによる。旧プロンプトのままでも、当時 1〜3 分・指摘 0 だった 4 PR で 6〜10 分かけ、テストを実行し、高の 1 件を再現した。当時の #740 は依存がなく better-auth のソースを読めなかったが、今回は読めている。
- 新プロンプトの上積みは、(1) 読み取り後の書き込みの質問による #723 の 1 件、(2) 閉じられなかった点を本文ではなく表の行にしたこと（#730）、(3) 本番設定で確かめたうえでの重大度（#740）、(4) 低の指摘 2 件。
- 新プロンプトでも 6 件中 4 件は出ていない。#730 は質問をしたうえで「後勝ち」を許容した。当時のリポジトリには「batch 内で再確認し、負けた側は CONFLICT」というルールがまだなかった（現在は `api-data-integrity.md` にある）。

## 測定後の変更（未測定）

測定で外れた 4 件に合わせて、次を足した。再生はしていない。

- 「読み取り後の書き込み」に、成功を返したのに上書きされる・エラーを返したのに行が残る、は欠陥だという基準を明記した。
- 「既存の行に対する移行」「画面やメッセージが示す事実」の質問を足した。
- 認証ライブラリの既定値の例に、保存形式・セッションの鮮度・トークンの寿命を足した。
- 保護がないと報告する前に、テスト環境が保護を切っていないか本番設定で確かめる、を足した。

## 限界

各条件 1 回で、ばらつきは測っていない。質問は同じ全体レビューの別の PR の指摘から作っており、独立した未知の PR での確認ではない。再生は CI の runner ではなく、ツール制限は指示によるもので、権限では強制していない（旧プロンプトの #740 は許可外の読み取りコマンドを数回使ったと自己申告した）。投稿、スレッド解決、2 巡目は測っていない。
